# figure-engine

The figure feature draws math figures (2D and 3D) from a JSON scene, using a Rust engine compiled to WebAssembly. It is developed test-first: write the failing test under `crates/figure/tests/`, see it fail, then write the code that makes it pass. The design and the extension list are in `docs/graph-design.md`; the human-facing explanation is `site/src/content/docs/dev/internals.mdx` — update both, and the pointers below, in the same commit as a scene-format change.

## The engine (`crates/figure/`)

Pipeline: `parse_scene` (JSON → `Scene`, checks the version) → `validate` (rules the types can't express) → `compile` (reads every expression, evaluates domains) → `render` (`Scene` + `Compiled` → the IR, `Figure`) → `tikz::export_tikz` (IR → TikZ text). `crates/figure-wasm/` wraps `parse_scene`/`render` for the browser with a typed `SceneOutcome`/`RenderOutcome`.

- `scene.rs`: the JSON types (`Object` enum, one variant and struct per object type, tagged by `type` in snake_case). `expr/`: the expression language (lexer, recursive-descent parser, evaluator), separate from the polynomial calculator's. Every built-in function takes exactly one argument (`sin`, `gamma`, `besselj0`, …; see `docs/graph-design.md` for the full list); user functions (`function` objects, `expr/functions.rs`) take one to three comma-separated arguments and are inlined into the caller's tree at parse time (`Expr::compile_with`), so everything downstream sees only built-ins. `expr/taylor.rs` computes Taylor coefficients by truncated power-series arithmetic (`Expr::taylor`) for the `taylor` object — the special functions (gamma, error, Dawson, Lambert W, Bessel at order 0/1) are thin wrappers around the `puruspe` crate, not hand-written numerics, so their correctness is that crate's.
- `validate.rs`: checks the types can't express (non-empty text, ranges, identifiers, plane-only/space-only placement, cross-object references such as a `cut`'s `surface` or a `tangent_line`'s `of`). Runs before `compile`, which re-checks anything that needs evaluated expressions (e.g., a literal `Bound::Number` is checked here for a quick error message, but an expression's value can only be checked after evaluation, in `compile.rs`).
- `transform.rs`: the shared `transform` field — `Affine` (3D matrix plus offset; plane points map as `z = 0`), `MapFn` (a compiled `map` object), and `Transform` (steps in written order, consecutive affine steps folded). `compile.rs`'s `compile_transform`/`step_affine` turn `TransformStep`s into it and own the step rules (exactly one operation, `axis` only on a space rotation, `shear` plane only); `Compiled.transforms` holds one per object. Where it is applied differs per object — see the Transforms bullet in `docs/graph-design.md` before adding it to a new type. `image.rs`: `expand_images` replaces each `image` by a transformed clone of its target; `validate` and `render` run on the expanded scene.
- `compile.rs`: reads every expression with `Expr::compile_with` (functions and maps are compiled first, in a pre-pass after parameters), evaluates domains and bounds, and builds `Compiled` (`parameters`, and one `Plot` per scene object in order). `Plot` is the per-object result of compiling (e.g. `GraphPlot`, `CurvePlot`, `TangentLinePlot`).
- `derivative.rs`: numerical differentiation (central difference), shared by tangent lines and tangent planes. Step size is a fraction of the parameter's domain width (`1e-6`, floored at `1e-9`), the same relative-step convention `refine.rs` uses for its numeric Jacobian.
- `sample.rs`: adaptive sampling of a curve/graph (16 fixed intervals, then halving to a chord tolerance). `clip.rs`: Liang–Barsky clipping of a sampled polyline to the view rectangle (plane figures only).
- `arrow.rs`: the `Stealth` arrowhead, ported from the pgf source. `hatch.rs`/`region.rs`: the parallel-line fill for a plane region. `figure.rs`: the IR (`Path`, `Label`, `Dot`, arrowheads, in cm with y up). `render.rs`: `Scene` → IR for a plane view (`render_plane`; space views delegate to `space.rs`). `tikz.rs`: IR → TikZ text; the scene JSON is never embedded in it, to keep the output short.
- `bezier.rs`: Bézier surfaces (`bezier_point`/`casteljau` on `Point3`) and Bézier curves (`bezier_curve_point`/`lerp_point` on dimension-agnostic `Vec<f64>`, shared by plane and space `curve` objects). `spline.rs`: spline curves (`catmull_rom_point`, uniform Catmull-Rom, the same `Vec<f64>` convention, plugged into `CurvePlot.spline` next to `CurvePlot.net`). `fractal.rs`: a declarative iterated function system (IFS) for the plane-only `fractal` object — its branches are `TransformStep` lists compiled to `transform::Affine` like any `transform`, and `instances` (the recursive deterministic IFS approximation: depth 0 is `[base]`, depth `n` is every branch's `Affine` applied to every path already produced at depth `n - 1`, so the path count is `transforms.len().pow(depth)` (summed over every depth with `all_depths`); `validate.rs` caps `depth`, `base.len()`, `transforms.len()`, and that product before `compile_fractal` ever calls it). An earlier prototype used L-system string rewriting and turtle-graphics interpretation instead; it was replaced because a turtle walk cannot express a disjoint construction (a Cantor set's gap) or an area-based one (a filled Sierpiński gasket) without contortion, while an IFS is the literal mathematical definition of self-similarity.
- `surface.rs`: the triangle mesh for a formula or Bézier surface, its outline (silhouette), and the visibility test (`Mesh::hides`, bucketed in a screen-space grid; `Mesh::hides_exhaustive` is the brute-force reference the tests check it against). `refine.rs`: polishes a cut's or intersection's mesh-derived curve onto the exact surface with Gauss–Newton, then thins and refines it (Douglas–Peucker plus adaptive midpoint insertion) so vertex density follows curvature.
- `space.rs`: `Scene` → IR for a space view. `build_space` assembles the `Space` (camera, `meshes` from every `Surface`, `complex_meshes` from every `Complex` and `Polyhedron` (both go through `as_complex`) — kept separate because a complex's own edges are never ray-tested against its own mesh, see below —, per-surface `SurfaceMap` closures, and the `mesh_of`/`surface_domains` lookups by id that cuts, intersections, and tangent planes use). Hiding is a ray test against every mesh, complex mesh, and sphere (`Space::hidden`); a line is stepped and bisected at the switch points (`split_by_visibility`). A complex's own edge is hidden by its own solid through a different, exact test instead (`Space::hidden_by_others` skips the complex's own mesh; `complex_edges` precomputes each edge's one or two adjacent face normals, and the edge is self-hidden when all of them face away from the camera). `wireframe_line` (used by `surface_wireframe_items` — at the `u`/`v` values `compile.rs`'s `wireframe_values` derived from `wireframe_step`: every multiple of the step strictly inside the domain, default step a quarter of the domain width — `control_net_items`, `sphere_wireframe_items`, and a tangent plane's edges) takes a `default_line: Line` parameter — dotted for a wireframe or control net, solid for a tangent plane, since the latter is real content, not a reference aid.
- Object types added after the first figure and the minimal space figure (each with its own `tests/*.rs`): Bézier surfaces/curves, spline curves, tangent lines (plane, `tests/tangent.rs`) and tangent planes (space), wireframes and the Bézier control net (`tests/wireframe.rs`), fractals (`tests/fractal.rs`), complexes — a solid built from `vertices` and `faces`, space only (`tests/complex.rs`; see the Complex bullet in `docs/graph-design.md` for how it hides itself), polyhedra — a regular solid given by `solid`, `center`, and `radius`, turned into a `Complex` by `polyhedron.rs` (`tests/polyhedron.rs` checks the fixed face lists mechanically), polygons (`tests/polygon.rs`), images and transforms (`tests/transform.rs`), user functions (`tests/user_functions.rs`), and Taylor polynomials (`tests/taylor_series.rs`, `tests/taylor.rs`). Adding a new object type touches `scene.rs` (the struct and `Object` variant), `validate.rs`, `compile.rs` (the `Plot` variant — `Plot::None` is enough for a type with no expressions to evaluate, as `Sphere` and `Complex` both show), `render.rs` and/or `space.rs` depending on which views it supports, `site/public/schema/scene.schema.json`, and the figure-editor files below.

## The JSON Schema

`site/public/schema/scene.schema.json` (served at `/math-study/schema/scene.schema.json`) is hand-written, not generated from the Rust types, and kept honest by `site/src/figure/scene-schema.test.ts` and `scene-schema-invalid.test.ts` (ajv, draft 2020-12; the shared setup is `scene-schema-support.ts`): every real figure and every editor-default object must validate, and a set of invalid scenes must fail. Update the schema, and its `description` fields, whenever the scene format changes. A rule the schema can't express (cross-object references, range ordering, id uniqueness) gets a note in the field's own `description` instead ("スキーマでは表せない").

## The editor (`site/src/figure-editor/`, no React)

- `draft.ts`: the scene draft and its operations (`rotateView` for drag-to-rotate, `NO_SELECTION`/`indexOfId`).
- `defaults.json`: the initial object per type, keyed by type then by `plane`/`space`.
- `create.ts`: `OBJECT_TYPES` (the add-menu list) and `createObject`. A variant distinguished only by an extra field — a Bézier or spline curve (`curve` + `bezier`/`spline`), a Bézier surface (`surface` + `bezier`) — is listed as its own type (`bezierCurve`, `splineCurve`, `bezier`) and mapped back to the real `type` on write; see `listedType`/`stemOf`.
- `fields.ts`: the input-field table per type (`FieldSpec`, whose type lives in `field-spec.ts`; the select options live in `field-options.ts`), including `toggleStyle` for a field that's present only when drawn (a surface's or sphere's `wireframe`, a Bézier surface's `control_net`; a surface's `wireframe_step` is a plain optional `list` field (two `bound`s) next to it, not part of the toggle, so it needed no change to `ToggleStyleInput` itself), `reference`/`references` for a field that names another object's id, and `transform` for the shared transform field (`field-transform.tsx` with the step picker from `transform-templates.ts`, added automatically to every type in `create.ts`'s `TRANSFORMABLE`), and `json` for a field with no dedicated input (a complex's `vertices` and `faces`, entered as raw JSON, the same way a fractal's `base`/`transforms` already are).
- `values.ts`: pure helpers that read and write field values. `json.ts`: the `Json` type.
- `edit-scene.ts`: `buildEditScene` builds the editable view's aids (reference styling, generated ticks) — a surface's or sphere's wireframe, and a Bézier surface's control net, are real engine-rendered scene fields, not editor-only aids, so this file does not touch them.
- `samples.ts`, `sample-scenes.ts`: the "見本" (samples) — complete drawings usable as they are, never single-feature demos (a bare Bézier patch or a lone spline belongs in the templates). `samples.ts` lists them (`EDITOR_SAMPLES`, plane first, then space): most are real article figures (`site/src/figures/*.json`, loaded with `import.meta.glob` and parsed with `parseDraft`; `withSurfaceAids` turns on every surface's `boundary` and `wireframe` and every sphere's `wireframe` on load, and nothing else differs from the article), the rest are code-defined scenes in `sample-scenes.ts` (the ellipse with its foci; the Taylor polynomials, composite function, and grid-under-a-map in `analysis-sample-scenes.ts`; the cylinder cut by a plane, the helix on a cylinder, the torus, the Möbius strip). A sample replaces the whole draft (`onLoad`). Every surface in a sample or template has `boundary: true` and `wireframe` (and, when code-defined, `wireframe_step`), and every sphere has `wireframe`; `templates.test.ts` checks this. `boundary` is safe everywhere because the engine skips seam and degenerate edges (`Mesh::boundary`), so no rim is drawn as a separate curve.
- `templates.ts`, `template-types.ts`, `fractal-templates.ts` (with `fractal-parts.ts`), `function-templates.ts`, `curve-templates.ts`, `bezier-templates.ts`, `surface-templates.ts`, `scene-templates.ts`, `insert-template.ts`: the "テンプレート" system. テンプレート(部品) (`OBJECT_TEMPLATE_GROUPS`, filtered by the draft's plane/space kind) are building blocks, and each group aims to be comprehensive rather than one example: 正多角形 (one `polygon` object each), フラクタル (`fractal-templates.ts`, the major IFS fractals on a unit shape, sized by the `transform`'s `scale`), 2次曲線, 平面曲線, and 空間曲線 (`curve-templates.ts`), 関数のグラフ (`function-templates.ts`, one `graph` per function, domains avoiding poles), ベジエ曲線・スプライン曲線 and ベジエ曲面 (`bezier-templates.ts`, several degrees, surfaces with `control_net`), 正多面体 (one `polyhedron` object each, so resizing is one number), 2次曲面 and いろいろな曲面 (`surface-templates.ts`, all with a wireframe and a `wireframe_step`). テンプレート(図) (`SCENE_TEMPLATES`, `scene-templates.ts`) are empty starting frames that replace the draft: empty, axes with the origin label O, and axes with a grid, each for plane and space. `insert-template.ts`'s `insertObjects` renames every object in a group to fresh ids (via `uniqueId`) and rewrites the group's internal `reference`/`references` fields (`fields.ts`) to match, leaving a reference to an object outside the group untouched. `templates.test.ts` renders every template and every sample through the real Wasm engine to confirm it is valid, not just schema-shaped, and requires `boundary` and a wireframe on every template and sample surface and a wireframe on every sphere.
- `download.ts`, `tikz-document.ts`: file export (JSON, TikZ). `image-formats.ts` (the format table, resolutions, `isTransparent`; JPEG is the one format without transparency) and `image-export.ts` (browser only): image export. `image-export.ts` typesets every label with `site/src/figure/label-svg.ts`, builds a standalone SVG with `site/src/figure/export-svg.ts`, and for PNG/JPEG/WebP draws it on an `OffscreenCanvas` at the chosen dpi, filling the canvas white first when the background is opaque (the SVG's own background rectangle leaves semi-transparent edge pixels after rounding to whole pixels). The toolbar (`image-export-controls.tsx`) imports `image-export.ts` dynamically, so MathJax's SVG output loads only on the first export.
- `site/src/figure/export-svg.ts`: IR plus typeset labels to a standalone SVG file. It reuses `svg.ts`'s `drawnElements`, replaces the `var(--figure-*)` colors with `LIGHT_COLORS` (checked against `figure.css` by a unit test), places each label in a TikZ-sized box (10 pt, 0.3333 em padding) at its anchor, and grows the canvas to fit labels that overflow the bounds. `label-svg.ts` is a MathJax document separate from the page's CHTML one, built from the ES modules with `liteAdaptor`, `fontCache: 'none'` (glyphs as paths, so the file needs no fonts), and `linebreaks: { inline: false }` (otherwise MathJax 4 splits `x+y` into several `<svg>` pieces). Its TeX packages are in `label-tex-packages.ts`. The font's extra glyph files are listed by package name in `label-font-files.ts` (a unit test checks the list is complete); a `/node_modules` glob fails on the dev server, see `docs/tech-decisions.md`.

`site/src/components/figure-editor/`: the React island. `figure-editor.tsx` (shell), `toolbar.tsx` (見本 loads a sample; テンプレート(部品) inserts an `ObjectTemplate` into the current draft via `use-draft.ts`'s `insert`; テンプレート(図) loads a `SceneTemplate` like `onLoad`; each picker's `key` includes the view kind so its selection resets when the kind changes), `form-panel.tsx`, `object-list.tsx`, `field.tsx` with `field-basic.tsx`/`field-special.tsx`, `style-input.tsx` (`StyleInput` for any `Style`-shaped field, `ToggleStyleInput` for a toggle-present field), `use-figure-renders.ts` (renders both the editable and the output scene), `preview.tsx` (editable, draggable) and `output-preview.tsx` (the real output, static), `use-drag-rotate.ts`, `use-draft.ts` (localStorage autosave; also owns `insert`, the id-safe template-insertion entry point). The engine validates everything and its rendering is never altered; the editor only builds JSON, including the editable view's aids. `site/src/content/docs/figure-editor.mdx` is the public page.

## Rendering `<Figure>` in content

`site/src/plugins/rehype-figures.ts` replaces `<Figure src="name" />` with the rendered figure, before `rehypeMathjax`. It loads `site/src/wasm/figure_bg.wasm` with `initSync` when `astro.config.ts` is read, so `mise run wasm` must have run first (the mise tasks that need it already do). `name` is lowercase letters, digits, and hyphens, and names `site/src/figures/<name>.json`; the dev server does not watch scene files (touch the MDX file to see a change). A `<Figure id>` is numbered like a statement (label `図<pageId>-<n>`) by `rehype-statements.ts`, which passes `label`/`anchor` to the element for `rehype-figures.ts` to turn into the `<figure>`'s `id` and a `<figcaption>`; see the `write-content` skill for the authoring side (`<Ref>`, `caption`).

`site/src/styles/figure.css` holds the SVG's per-name color variables (light/dark) and the palette that `\colored{...}` in math shares (see the `write-content` skill). `site/src/projection/camera.ts` re-derives the projection basis in TypeScript and is checked against the Rust engine in `camera.test.ts`; `site/src/components/projection/` is the sliders island that draws a space figure in the browser through `site/src/figure/hast-react.tsx` (SVG IR → React elements). It runs MathJax in the browser for labels, so it needs the same `menuOptions.settings` speech/braille workaround as the calculator (see the `rust-wasm` skill).

## Verifying a figure change

The TikZ golden file (`crates/figure/tests/golden/`) is compared by both `cargo test` (`tests/tikz.rs`) and `site/src/figure/wasm.test.ts`; regenerate it with `UPDATE_GOLDEN=1 cargo test -p figure --test tikz` and read the diff before committing it. A change to the drawing itself (scene fields, arrowheads, dash patterns, label anchors) also needs `mise run tikz` to pass — see the `verify-site` skill for that and for the Playwright `boundingBox()` pitfall when measuring figure geometry in a test.
